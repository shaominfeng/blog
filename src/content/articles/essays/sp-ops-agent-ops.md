## 写在前面

这篇文章记录我最近用 Agent 做 SP-OPS 运维工具的经过。它算不上"AI 一次就做对"的故事。大部分时间是我指出哪里不对，Agent 去查，改完，我再找下一个问题。与其说成品有多好，我更想讲的是这个来回是怎么走的。换一个项目，这套做法大概也用得上。

时间跨度是 2026-10-21 到 10-29，中间开了十几个会话。文中内容来自会话记录和 git 提交历史，内部域名、IP、数据源 ID 和凭据都已去掉。

## 一、发现问题：文档和真实环境对不上

### 1.1 起点

这一切要从换团队说起。我刚从一个团队调到另一个团队，周围的一切都是陌生的：代码不熟，环境不熟，以前用惯的工具大多用不上了。我便让 AI 带着我熟悉产品代码，也熟悉这里的运行环境。

之后老板交给我一个优化 Redis 使用的任务。这个任务不着急，却正好是熟悉全局的好机会。我没有一上来就铺开，而是从 Redis 这一个点的问题出发，借着 AI 对异常的敏感，一步一步往下做。做着做着，我自己摸索出了一条能监控整个产品线的工具。

我先想看看 Redis 的现状，于是打开 Grafana Portal 看指标。看了一会儿就觉得吃力。站点多（US、EU、SG、AU、IN 等），每切换一次都要重新找面板，还得一直盯着变化，人的精力很快就不够用了。我心里冒出一个念头：能不能让 AI 来盯？

要让 AI 盯盘，先得知道去哪查、怎么查、能拿到什么。我翻了一下 Grafana，发现它可以生成 API Key，程序能直接取数。那让 AI 去摸这套接口，说不定能拿到比页面上还多的东西。第一版 `grafana-ops` skill 就是这么来的。

第一版文档只列了 5 个 dashboard 和几个数据源，看起来能用，实际覆盖很不全。10-21 我让 Agent 验证文档里写的能力，原话很简单："探索 grafana 的能力，dashboard 可以加进去，看看还有没有漏掉的。"

### 1.2 第一轮探索

Agent 把 39 个 dashboard 的面板定义全部读了一遍，再和 skill 文档逐项对照，差距如下：

| 项目 | 文档原来的写法 | 实际情况 |
|---|---|---|
| Dashboard 覆盖 | 5 个 | 39 个 |
| 站点 | 没有区分站点 | 5 个站点，每个站点是独立的 Grafana 实例 |
| 数据源 | 标为 "prod EKS" | 实际只覆盖 US 节点，并非全局 |
| 能力声明 | 写成固定结论（如"无权限"） | 会随环境和 Key 变化，需要每次先尝试 |

有一处错误我记得很清楚。Agent 一开始把某个数据源当成 "prod EKS" 来用，依据只是部分指标带了集群标签。我问它："你看的是什么 site？这个应该要区分环境吧？" 它核对之后承认，之前的判断没有依据，查的其实只是 US 节点。

### 1.3 粒度和 CPU 口径

还有两个更隐蔽的问题。

第一个是粒度。我让 Agent 画 1 小时粒度的曲线，它发现 CloudWatch 数据源会无视传入的 `period`，改为按时间范围自动选择：2 天用 5 分钟，7 天用 15 分钟，30 天才是 1 小时。之前按"小时"统计的 7 天数据，实际是 15 分钟粒度，小时数被放大了 4 倍。这是 Agent 核对曲线时自己追出来的，当时我没有看出来。

第二个是 Redis 的 CPU。最初用的是主机的 `CPUUtilization`，`sp-redis-us-001` 排在最前面。换成 `EngineCPUUtilization`（Redis 单线程引擎的真实负载）以后，它只有 20% 左右，反倒是 `sp-redis-us-002` 和 `sp-redis-sg-001` 的引擎线程经常打满 100%。结论整个反过来了。

## 二、把"错"分类

来回改了大约一周，我把遇到的问题归成四类。后来这套分类直接变成了 Agent 做校验和审查时用的清单。

- 口径问题：站点与环境没区分，指标选错（主机 CPU 与引擎 CPU），粒度被数据源悄悄改掉。
- 事实问题：文档里的结论没有实测，比如"跨 region 可以查"、节点数量、数据源 ID。
- 规则问题：严重程度只看历史窗口，问题已经恢复，告警却还在。
- 工程问题：脚本的错误被当成正常结果，退出码不统一，限流没有重试。

其中第三类影响最大，第四节细说。

## 三、方案：先探索，后监控

### 3.1 拆成两层

最初的需求是一个资源监测 skill：写清楚有哪些资源、怎么查、怎么分析，最后出报告，异常项给出合理的分析。

后来我把"探索"和"监控"拆开。原因是想让 `grafana-ops` 以后能给别人用。它的定位接近 MCP，只负责供数：按站点和环境查指标，列出 dashboard，返回逐日或逐小时的序列，不做任何判断。

判断交给别的 skill。`resource-inspection` 就是其中一个，回答的是"有没有风险、多严重、会不会变坏"。以后再有分析类的 skill，可以直接复用同一份数据层，不必各自写一套查询。

这条边界最早是校验子代理在 10-22 提出的：第一版监控 skill 把单值查询也交给了 `grafana-ops`。10-28 加 Pod 探索方案时，我又强调了一次：数据层只管供数，判断全部放在分析层，两边靠文档约定交接。

### 3.2 阈值要有出处

我让 Agent 参考公开标准来定阈值。它上网核对了 AWS 的官方建议，结果发现 AWS 并没有统一的数值，第三方资料给出的数字也差得很远。

所以每个阈值都标了来源和性质。比如 Pod CPU 限流的 25%/5 分钟，来自 kubernetes-mixin 的规则。阈值集中放在 `thresholds.json`，来源写在 `thresholds.md` 里。

### 3.3 先当 Skill 跑真实数据

第一版直接放在 `~/.claude/skills/` 下，拿真实数据跑。每改一次，就用 US、EU、SG 近 30 天的数据重跑一遍，和我之前手动分析的结论对照。不少问题就是这样跑出来的。

## 四、多轮修正

### 4.1 先确认站点，再查询

第一条规则是：每次查询前先确认站点和环境，不默认 US，也不沿用上一次的。`SKILL.md` 里加了一张 Site 对照表，写明每个站点的 CloudWatch region、Redis 示例和数据源。

之后再遇到"查一下 Redis"这种泛泛的请求，会先问清资源类型和站点，不会直接跑脚本。

### 4.2 严重程度

这是整个过程中改得最要紧的地方，前后改了两次。

第一次是在 10-22，改的是"会不会变坏"。第一版只看历史。我指出 `sp-redis-us-002` 的引擎 CPU 尖峰"就一天"，后面已经解决了，不该算严重。Agent 重新梳理之后，把严重定义为"按当前趋势 14 天内会耗尽，或近期已经到了严重水平"；警告是"近期仍异常，但趋势持平或回落"；提示是"只出现在历史窗口里，近 3 天没有复发"。

"上升"的判断也需要比例阈值。Agent 起初设成 1.5，我看结果时发现有个我认为不该算严重的节点被判成了严重，于是改成 2.0。

第二次是在 10-29，改的是静态阈值。我看到一份报告：某 Redis 节点 10-26 内存峰值接近 100%，之后已经回落到 1% 以下，报告却还标着严重。我问："这个问题前天就解决了，昨天已经降下来了，为什么还在告警？是不是 skill 计算有问题？"

Agent 查完承认，问题出在规则上：`level_check` 只看报告生成前 3 天的窗口，不看当前值。它又用只读查询拉了逐日数据，确认节点确实已经回落。

修法还是我先定标准，它来实现和验证：

- 静态阈值改为看最近的数据点，最近 3 个点全部越线才算当前严重。
- 我接着提出"所有的严重线都要看最近的情况"。Agent 盘点出五类判定逻辑（静态阈值、均值、尖峰、耗尽外推、淘汰），逐一加上"近期仍越线"的条件。
- 耗尽外推改用近期斜率算天数，近几天斜率已经回落，就不再判为严重。

做完之后我的体会是，阈值看上去是技术参数，其实是运维判断。数字 AI 能算，"什么算严重"得由人来定。

### 4.3 独立校验

这一步用到的是 `skill-design-standards`，是我自己沉淀的一套 skill 编写标准，管新 skill 的创建和改造。它把 skill 当成给机器读的资产来设计：目录结构固定，description 要能明确判断触发和排除，SKILL.md 不超过 500 行，确定性的逻辑下沉到脚本，最后必须过完整验证。

验证分四个 Pass：描述与路由、逻辑、边界与失效模式、结构合规。新 skill 四个全跑，每个 Pass 由独立子代理执行，只给它任务边界和校验提示词原文，不给我们的实现思路。每次结果都写进 `validation-log.md`。配套的 `lint_skill.py` 负责机器能查的部分，比如 name 格式、description 长度、行数。

项目里有两处用到。resource-monitor（后改名为 resource-inspection）是从零创建的，按新建流程跑完四个 Pass；grafana-ops 瘦身时，按改造流程跑 Pass 1、2、4。

结果大致如下：

- 第一轮 Pass 3 列出了 42 条失效模式，多数在新版脚本里已经修掉了，但仍有一批真实缺口。
- resource-monitor 的 Pass 2（逻辑）复跑了很多轮，到 10-22 交接时还是 NOT CLEAN，每轮都会冒出新的阻塞项。
- 独立代码审查找出了我们自己没发现的问题。比如 30 分钟的查询步长让"重启次数"漏记了大部分事件，单点序列还会除零。

Agent 在某一轮结束时写了一句："这个 skill 目前不能称为'已验证通过'。" 这句话原样留在了 `validation-log.md` 里。每轮结果都如实记录，没有重跑的 Pass 不写成通过。

最后的处理很朴素：矛盾项修掉，剩下的标成"已知限制"，由我来定。这比硬说"已验证"靠谱。

### 4.4 一个小 bug

报告里 `sp-redis-us-002` 的峰值时间写的是 10-03。我说："这个是在10.3号就一天吧。" Agent 核对后发现，脚本取的是峰值第一次出现的时间，而不是最近一次。看报告的人会以为事件只发生在那一天。

这件事让我更加确信，报告里的每个数字都得能回到原始数据去核对。

## 五、拿真实问题检验

### 5.1 uic-web-server：要不要扩容

第一个真实问题来自工作。我想知道 US 的 `uic-web-server` 是什么服务，内存配得够不够，要不要扩容。

Agent 先确认它是 XDR Portal 的前端服务，nginx 托管静态资源，反向代理到 API 网关。然后它查出：10 个 Pod 全部正常，HPA 范围是 5 到 20，没有触顶，近 24 小时没有重启和 OOM。

但单 Pod 的内存 request 是 256Mi，实际用量在 245 到 285Mi 之间，内存 HPA 一直在 95% 到 110% 之间晃。也就是说，副本数是被内存顶上去的，和流量关系不大。

结论是不需要加副本，该调的是内存的 request 和 limit。Agent 还找到了参数定义所在的运维部署仓库，检查了一个相关的调整 PR，方向和我们的建议一致。我又让它看其他站点，情况类似，只是 US 的 limit 最紧。

我把结论和证据发给了运维。运维核对后确认了问题，很快就有一个 PR 上线，没有拖下去。这是 Pod 探索能力第一次派上真正的用场。

### 5.2 horus-connector：从一条限流告警追到上游

第二个问题复杂得多，也更能说明这套做法的用处。

起点是巡检报告里的一条：`horus-connector` CPU 限流，跨站普遍存在，US、EU 严重，SG、IN、AU 警告。往下看 Pod，US 和 EU 的每个 Pod 只有 1 核 limit，HPA 已经到了上限 10，Pod 一直在被限流，内存却只用了不到 10%。

我把这条发给了运维。运维的判断是：这是代码问题，调 resource 解决不了。我没有就此停下，想看看代码里到底出了什么问题，于是让 Agent 接着往下查。我这边只给方向，先看趋势，再看依赖，再看日志。具体用什么工具、下一步查什么，基本都是它自己定的。

它的路径大致是这样的。

先看代码。有些重试循环没有退避，定时同步每分钟触发一次。这两处能解释 US、EU、SG 的 CPU 为什么全天平稳，没有昼夜波动。不过每分钟触发同步的调用方，在这几个仓库里找不到，应该在集群外的调度器上。

再看部署仓库。它一开始信了代码仓库里的 Helm chart，后来发现和运行中的 Pod 对不上，才找到部署仓库里的 prod values，确认那才是运行值的来源，并主动更正了之前的说法。这份配置自 2024 年 4 月起就没有改过，所以饱和不是配置变更造成的。

然后拉 30 天趋势。2026-10-20 19:00 UTC 前后，EU、SG、AU、IN 四个站点的限流和 CPU 同时阶跃上升，之后一直停在高位，镜像和 values 都没有变。巡检默认只看 7 天，这个台阶其实已经持续了一周多，之前没有人注意到。

接着查依赖和上游。同一时刻，portal-backend 的 CPU、DocDB 读操作、Redis 网络流入也一起上了台阶，而 Redis 和 DocDB 的 CPU、连接数基本持平。依赖没有饱和，变的是调用量。

最费劲的是日志这一步。用 slog-query 查，一开始结果全是 0。Agent 自己换了索引名，又发现 uri、来源 IP 这些字段没有被索引，无法直接过滤。它改成按时间窗口随机抽样，再用来源 IP 和 Pod 的存活时间去匹配调用方。结果是两段增长叠在一起：

- 10-20 19:00 起，某个汇总类接口的请求来源从集群内切到了集群外的几个网段，EU 的 horus 总量从约 112 万/小时升到 134 万。
- 从 23:00 起，出现了一个集群外的客户端，只调 foundationInfo 接口，每次请求对应一个不同的客户，成段出现，段与段之间间隔 5 到 15 小时，每一段的来源 IP 都不一样。看起来像一个按客户逐个遍历的批量任务。那几个小时里，这个接口占了 portal-backend 调用量的 60% 左右，平时几乎是 0。

最后回到代码。Agent 在本地工作区里找这两个接口的调用方，找到了路由定义和一部分调用方，唯独没有找到发起遍历的代码。这说明发起方不在这些仓库里。

日志里还有两个旁证。遍历期间，其他调用方的 p50 延迟从约 2ms 升到 8 到 26ms，遍历结束后恢复，说明 horus 在高负载下排队，已经拖累了别人。另外，horus 的缓存命中率只有 4% 到 13%，大部分请求都落到了 Redis。

所以运维最初的判断只对了一半。代码确实有可以改的地方，比如重试退避和缓存命中率。但 10-20 之后 CPU 的阶跃式上升，更像是上游调用量变了。只加 resource，或者只改 horus 自己的代码，都碰不到根上。那些集群外网段到底属于谁，还需要网关或 VPC 的数据才能确认。目前没有结论，抽样得到的占比也有几个百分点的误差，只能说明量级。

回头想，这条线上每个工具都只能看到一角。监控只知道"CPU 满了"，日志才看得到是谁在调，代码才能判断调用方是不是在自己手上。工具接得越多，能追的链条就越长。

### 5.3 fed-svc-prod-001：从告警到修复，再到告警消失

第三个问题跨度最长。从 10-22 的第一份巡检报告，到 10-29 告警降级，整条线在报告里都留有记录。

起点还是巡检。US 的 `fed-svc-prod-001` 和 `-002`（同一个服务的两个 Redis 节点）第一次跑就被标成严重：内存约 78%，近 7 天每天涨 9 个百分点左右，按这个速度几天就会耗尽。我先怀疑是不是误报，10-23 让 Agent 拉了 14 天的逐日内存来确认增长形状。曲线很平滑，一路涨到 86.9%，不是噪点，是真的在涨。同时我让它整理了一份给服务负责人的排查清单，列出查证命令和需要确认的发布记录。到 10-24，内存已经在 99% 以上，002 开始出现 key 淘汰。

接着往代码里找原因。10-27，我让 Agent 研究这个服务的仓库里 Bull（Redis 任务队列）是怎么用的，失败的任务会不会被清理。它读完代码的结论是：没有专门的清理逻辑。

- 大部分任务没有设 `removeOnComplete` 和 `removeOnFail`，Bull 默认永久保留。
- 任务链最后一环执行完之后，没有代码去删这个任务，已完成的任务一直留在 Redis 里。
- 失败的任务只在最后一次重试时才会被删，删不掉的就一直躺着。
- 整个仓库没有按时间清理的机制。

也就是说，队列里的任务只进不出，Redis 内存被一点点占满。

修复也交给 Agent 来做。它加了队列状态的监控接口和手动清理接口，又加了定时清理，已完成和失败的任务只保留 1 天。改动提了 PR，合入后部署上线。

上线后，10-27 18:21 UTC（北京时间 10-28 02:21）前后，两个节点的 key 数在几分钟内从约 30.7 万掉到约 600，内存从 99% 以上降到 1% 以下，淘汰也停了。

监控这边还有一段尾巴。10-28 和 10-29 凌晨的两份报告里，这两个节点依旧标着严重，因为当时的规则只看历史窗口、不看当前值，也就是 4.2 里说的那件事。规则改掉之后重跑，US 的严重数从 4 降到 0，两个节点变成"提示：近期曾达严重水平，当前已回落"。

每一期报告都存了档，回头对照就是一条完整的记录：

| 报告日期 | 级别 | 当时的数据 |
|---|---|---|

## 七、复盘

回头看，有几条我觉得换个项目也用得上。

1. 让 AI 去查，别让它解释。每个结论都要能回到查询结果、脚本输出或配置文件。Agent 表现最好的几次，都是在我质疑之后它真的去查了。
2. 一条告警要往外追，别停在第一个解释上。horus-connector 一开始被判成代码问题，顺着监控、部署仓库、日志、代码一路查下去，才发现 10-20 之后上游的调用来源变过了。工具接得越多，能追的链条越长。
3. 口径先对齐。同样叫 CPU，主机口径和引擎口径的结论正好相反，数据源还会悄悄改粒度。监控看的是现在，历史窗口只适合回溯事件，不该拿来定严重级别。
4. 校验要真的独立。子代理只拿到任务边界和提示词原文，我们的判断一概不给，这样才找得出我们自己看不到的 bug。没有闭环的项也要写出来，校验日志逐个 Pass 记录，没重跑的不写成通过。
5. 往公开仓库同步之前，先查可见性和历史。同步 skill 到 marketplace 之前，Agent 发现远端 main 上已经有含内部信息的文件。它没有擅自提交或推送，而是把情况列出来，让我逐项确认。教训是同步前就得查，别等出了事再补。
6. 凭据不进对话，也不进文档。Key 一律从环境变量读取，只检查长度，不输出内容。提取部署配置时，带密码的行要先过滤掉。
7. 判断由人来做，执行和核对交给 AI。严重程度的口径、比例取 2.0 还是 1.5、哪些只能标成已知限制，都是我拍板的。

### 8.3 报告长什么样

每次巡检生成一份 Markdown 报告，结构固定，分六块：

1. 标题与元信息：站点、资源类型、查询窗口、数据源、查询数与失败数，以及覆盖范围。
2. 结论概览：严重、警告、提示各几项，并按优先级列出要先处理的条目。
3. 数据覆盖与质量：每个节点的数据点数、粒度和缺失说明，例如"某 Pod 未设置 limit，内存比例规则无法判定"。
4. 资源明细：按站点列出每个节点的关键指标。
5. 异常与分析线索：每条发现包含级别、对象、指标、规则、证据、可能原因和查证方式。
6. 严重程度定义与方法阈值：写明判定口径，方便别人复核。

下面是一条发现的示意（已脱敏）：

```markdown
### [严重] US / 某 Redis 节点：内存使用率：近期已达严重水平

- 规则：`redis.memory_peak`
- 证据：近 3 天最高 99.84%；最近一次 10-27 09:34 UTC（北京 17:34）
- 可能原因（待验证）及查证方式：
  - 内存接近 maxmemory，需确认 maxmemory-policy；查证：CONFIG GET maxmemory-policy
  - 节点规格偏小；查证：核对节点类型的内存上限
```

报告里的"可能原因"都只是待验证的假设，每条都附了查证方式，不直接下结论。这一点是前面反复修改之后才定下来的。

### 8.4 怎么验证

- 离线测试覆盖规则边界：单点序列、停更节点、节流重试、全零数据、配置错误等。
- 真实数据回归：每次改规则后，用 US、EU、SG 的真实数据重跑，对比结论的变化，并核对变化的来源。前面那次警告从 8 条变成 11 条，就是这样查清的。
- 独立校验与审查：按 skill-design-standards 的四个 Pass 和独立代码审查复核，未闭环的项留在 validation-log 里，不包装成通过。
