## 餐厅的完整架构

### 整体架构图（形象展示）

![AI 系统餐厅架构图](/blog/images/restaurant-architecture.webp)

*图：AI 系统的 4 层餐厅架构 - 从顾客点菜到后厨出菜的完整流程（黑板手绘风格）*

**架构四层说明**：

**Layer 1 - 顾客层（蓝色）**：
- 顾客提出需求：「我要川菜宴席，8 人」
- 从 2022 年需要详细描述 → 2026 年只说目标

**Layer 2 - 前厅服务团队/推理层（金色），最重要**：
- **Agent 领班**（中央）：规划菜单、协调后厨、优化成本
- **助手系统**（左）：记录历史、传递需求
- **API Gateway**（右）：接待、收银
- 这层是**核心差异所在**：同样的主厨，不同的服务团队决定体验

**Layer 3 - 后厨/模型层（红色）**：
- **主厨（AI 模型）**：GPT-4、Claude Opus、DeepSeek-R1
- **记忆力演进**：4K → 100K → 1M（上下文窗口）
- **炉灶（GPU）**：火力大小决定速度
- **资源监控**：温度计（算力）、时钟（时间）

**Layer 4 - 工具资源层（绿色）**：
- **Skills 菜谱**（左）：《川菜大全》《法式甜点》= 知识、方法论
- **MCP 采购**（中）：菜市场、供应商 = 获取外部资源
- **Function Calling**（右）：刀、锅、铲 = 基础工具

**信息流动**（箭头方向）：
```
顾客点菜 → 服务团队理解规划 → 后厨执行烹饪 → 调用工具资源
```

## 各角色详细解析

### 1. 顾客（用户）

**角色**：提出用餐需求
**演进**：从「烹饪专家」到「说目标就行」

```
2022 年：必须是烹饪专家
"鸡肉切 1cm 见方，腌制 15 分钟，加生抽料酒..."

2026 年：只说目标
"给我一桌川菜宴席，8 人，预算 2000"
```

### 2. 前厅服务团队（推理层）最重要

**核心成员**：
- **领班（Agent 核心）**：规划、决策、协调
- **服务员（助手系统）**：记录历史、传递需求
- **前台（API Gateway）**：接待、收银

**领班的关键职责**：
```
理解需求：
"川菜宴席，8 人，预算 2000，有人不吃辣"
↓ 解析成
- 菜系：川菜
- 人数：8 人
- 预算：¥2000（约¥250/人）
- 约束：至少 1-2 道不辣的菜

规划菜单：
查阅《川菜大全》(Skills)
→ 设计：凉菜×3、热菜×6、汤×1、主食×2

协调资源：
- 检查库存（有什么食材）
- 采购清单（去 MCP 买什么）
- 安排炉灶（哪个 GPU 做什么）

优化流程：
- 凉菜提前做
- 热菜控制上菜节奏
- 汤慢炖，最后上

成本控制：
- 提前备好常用料（Prompt Caching）
- 收走空盘子（Auto-Compact）
- 只给主厨需要的菜谱（Skills 按需加载）
```

**为什么推理层最重要？**
```
很多人以为：AI = 主厨（模型）
实际上：AI 系统 = 主厨 + 服务团队

同样的主厨（同样的模型），不同的服务团队（推理层）：
- 差的服务团队：顾客说不清楚，后厨做错菜，成本高昂
- 好的服务团队：快速理解需求，优化流程，成本可控

这就是为什么：
Claude Code（Anthropic 的服务团队）> ChatGPT（OpenAI 的服务团队）
即使用的是同等级的主厨（模型）
```

### 3. 后厨（模型层）

**主厨（AI 模型）**：
- **大脑/技艺** = 模型参数（GPT-4, Claude Opus, DeepSeek-R1）
- **记忆力** = 上下文窗口
  - 新手（4K）：只记得 4 道菜
  - 大厨（100K）：记得 100 道菜
  - 特级大厨（1M）：记得 1000 道菜的所有细节

**炉灶（GPU/显卡）**：
- 火力大小 = 算力（H100 vs A100 vs 消费级显卡）
- 炉灶数量 = GPU 集群规模
- 火力越大，出菜越快

**电力（算力资源）**：
- 燃料供应 = 电力成本
- 决定能开几个炉灶
- 云端餐厅（无限电力）vs 家庭厨房（有限电力）

**仓库（存储）**：
- 存放食材、半成品
- 对应模型的中间计算结果

### 4. 工具与资源层

#### Skills（菜谱宝典）

**定义**：烹饪知识、方法论、最佳实践

**具体内容**：
```
《川菜大全》：
- 宫保鸡丁标准做法
- 火候控制技巧
- 刀工要求
- 摆盘风格

《法式甜点》：
- 马卡龙温度曲线（150°C 烤 15 分钟）
- 舒芙蕾打发技巧（打到湿性发泡）
- 焦糖制作要点

《粤菜精髓》：
- 煲汤时间表（老火汤 3 小时）
- 清蒸技巧（水开后蒸 8 分钟）

《烹饪宝典》：
- 刀工百科
- 火候控制
- 味道平衡
```

**特点**：
- ✓ 知识、方法论、标准流程
- ✓ 保证质量一致性
- ✓ 可复用（每次做宫保鸡丁都参考同一个配方）
- ✓ Token 效率高（只给需要的菜谱）

#### MCP（采购系统）

**定义**：获取外部资源的渠道

**具体渠道**：
```
菜市场接口：
- 新鲜蔬菜（本地文件系统）
- 时令水果（实时数据）

海鲜供应商：
- 深海鱼（数据库查询）
- 龙虾帝王蟹（API 调用）

调料仓库：
- 各种香料（工具集成）
- 酱料（第三方服务）

超市 API：
- 日常食材（常用数据源）

进口食品商：
- 罕见食材（专业 API）
```

**特点**：
- ✓ 连接外部世界（数据、服务、工具）
- ✓ 实时获取（动态数据）
- 代价：Token 消耗大（所有供应商信息都要告诉厨师）
- 代价：安全风险（不可信的供应商可能有问题）

#### Function Calling（基础厨具）

**定义**：最基础的工具调用能力

**工具清单**：
- 刀（切）
- 锅（煮）
- 铲（炒）
- 勺（盛）

**类比**：
- 就像厨师必备的基本工具
- 没有菜谱指导，也能「瞎炒」
- 但效果不稳定，质量难保证

## 点菜方式的演进史

### 2022 年：必须当烹饪专家（Prompt 工程萌芽）

**场景**：
```
顾客（需要非常详细的描述）：
"我要宫保鸡丁。
鸡肉切 1cm 见方的丁，用生抽、料酒、淀粉腌制 15 分钟。
花生提前用油炸至金黄。
干辣椒用朝天椒，剪成 2cm 段，去籽。
葱姜蒜切末，葱白葱绿分开。
糖醋比例 1:2，加酱油、料酒、淀粉调汁。
锅烧热下油，先大火爆香花椒 30 秒捞出。
下鸡丁中火翻炒 2 分钟至变色。
加干辣椒、葱姜蒜爆香 1 分钟。
下黄瓜丁、花生翻炒 1 分钟。
最后淋汁快速翻炒 10 秒出锅。"

厨师：严格按照描述执行（一个步骤错了就失败）

结果：
✓ 如果描述准确，能做出好菜
✗ 顾客必须是烹饪专家
✗ 描述稍有不清楚，菜就做错
```

**痛点**：
- 门槛太高（普通人不会这么点菜）
- 不稳定（细节没说清楚就失败）
- 不可维护（下次点菜要重新描述一遍）

### 2023 年：Prompt 工程师是高薪职业

**场景**：
```
顾客（需要专业知识）：
"宫保鸡丁，按川菜传统做法，鸡肉嫩，花生脆，
微辣，糖醋适中，不要太咸。"

厨师：理解基本要求，按标准流程做，但细节靠经验

结果：
✓ 比 2022 年好很多
✓ 成功率提高到 70-80%
✗ 顾客还是要知道“川菜传统做法”是什么
✗ 不同厨师理解不同，质量不稳定
```

**行业现象**：
- 出现专门的「点菜顾问」（Prompt 工程师）
- 年薪$20 万（2023 年真实数据）
- 专门研究「怎么说话，厨师才听得懂」

### 2024 年：厨师变聪明了（模型推理能力提升）

**场景**：
```
顾客（简化描述）：
"来个宫保鸡丁，微辣，花生多一点"

厨师（会推理了）：
"宫保鸡丁"→ 自动知道标准做法
"微辣"→ 减少辣椒用量
"花生多一点"→ 加量 20%

结果：
✓ 顾客不需要是专家
✓ 质量稳定（厨师有基础知识）
✓ 个性化（能理解偏好）
```

**技术突破**：
- OpenAI o1（推理能力）
- Claude 3（长上下文+推理）
- 厨师从「严格执行命令」到「理解意图」

### 2025 年：领班接管全流程（Agent 诞生）

**场景**：
```
顾客（目标导向）：
"给我一顿正宗的川菜宴席，8 个人吃，预算 2000"

领班（Agent）自主决定：
1. 【查菜谱】翻《川菜大全》(Skills)
   → 确定经典菜单结构：凉菜×3、热菜×6、汤×1

2. 【列清单】需要哪些食材
   → 鸡肉、鱼、虾、各种蔬菜...

3. 【去采购】调用采购系统（MCP）
   → 菜市场买新鲜菜、供应商拿海鲜

4. 【排计划】安排上菜顺序
   → 汤先炖（3 小时）
   → 凉菜提前做（可冷藏）
   → 热菜按时间倒推

5. 【协调后厨】告诉主厨按什么顺序做

6. 【质量检查】每道菜品尝，不满意重做

7. 【上菜服务】观察节奏，及时调整

8. 【最终确认】"川菜宴席已全部上齐，请慢用！"

顾客全程不用管细节，只等着吃就行
```

**关键突破**：
- 从「被动响应」到「自主执行」
- 从「每步确认」到「说目标就行」
- 从「单个任务」到「完整流程」

### 2026 年：多领班协作（多 Agent 系统）

**场景**：
```
顾客："办一场 200 人的婚宴，中西结合，预算 10 万"

餐厅经理（主 Agent）：
"这个任务太大，我来协调多个领班"

分配任务：
- 领班 A（中餐区）：负责 50 道中餐
- 领班 B（西餐区）：负责西式冷餐
- 领班 C（甜品区）：负责婚礼蛋糕和甜点
- 领班 D（酒水区）：负责饮料和酒水搭配
- 领班 E（协调员）：控制整体节奏

各领班自主工作：
- 同时查各自的菜谱（Skills）
- 同时去采购（MCP）
- 并行准备食材和烹饪
- 互相协调（"甜品区，主菜快好了，准备切蛋糕"）

最终：
经理："婚宴已准备就绪，请入席！"
```

**这就是 Claude Cowork 和多 Agent 协作的概念！**

## MCP vs Skills 深度对比

### 核心区别

```
┌─────────────────────────────────────────────────────┐
│ 关键区分 │
├─────────────────────────────────────────────────────┤
│ MCP（采购系统）= "我能拿到什么食材"（能力层） │
│ Skills（菜谱） = "我知道怎么做菜"（知识层） │
│ Function Call = "我有基本厨具"（工具层） │
└─────────────────────────────────────────────────────┘
```

### 详细对比表

| 维度 | MCP（采购系统）| Skills（菜谱宝典）| Function Calling（基础厨具）|
|------|---------------|------------------|---------------------------|
| **类比** | 菜市场、供应商 | 烹饪书、菜谱 | 刀、锅、铲 |
| **作用** | 获取外部资源 | 提供知识方法 | 基础工具能力 |
| **解决问题** | 「没有食材怎么办」 | 「不知道怎么做怎么办」 | 「怎么切菜炒菜」 |
| **Token 消耗** | 很大（50 个供应商信息）| 很小（按需给菜谱）| 中等 |
| **适用场景** | 需要外部数据 | 需要领域知识 | 基础操作 |
| **安全性** | 风险高（供应商可能有问题）| ✓ 安全（内部知识）| ✓ 可控 |

### 三种组合场景

#### 场景 1：只有 MCP，没有 Skills

```
厨师有采购能力，但不会做菜：

厨师："我能拿到龙虾、松露、鹅肝、鱼子酱"
（但不知道法餐怎么做，只能瞎炒）

结果：
食材：★★★★★（顶级）
技术：★（不会做）
成品：★★（浪费了好食材）

类比现实：
有 GitHub API 但不知道 code review 流程
→ 能拿到代码，但不知道怎么 review
```

#### 场景 2：只有 Skills，没有 MCP

```
厨师会做菜，但拿不到食材：

《法餐圣经》写着：
"用龙虾、松露、鹅肝制作..."

但厨师出不了门（无采购能力）
只能看着菜谱流口水

结果：
理论：★★★★★（完美配方）
食材：✗（没有）
成品：✗（做不出来）

类比现实：
有 code review 的最佳实践，但拿不到代码
→ 知道怎么 review，但无代码可 review
```

#### 场景 3：MCP + Skills（完美组合）

```
厨师既会做菜，又能采购：

顾客："来道法式海鲜汤"

1. 【查菜谱】打开《法餐圣经》(Skills)
   → "需要：龙虾、扇贝、白葡萄酒、藏红花..."
   → "做法：先熬高汤 2 小时，加海鲜..."

2. 【去采购】调用 MCP
   → 海鲜供应商拿龙虾、扇贝
   → 酒水商拿白葡萄酒
   → 香料商拿藏红花

3. 【按菜谱制作】
   → 严格按《法餐圣经》的标准流程
   → 火候、时间、比例都精确控制

结果：
食材：★★★★★
技术：★★★★★
成品：★★★★★（完美）

类比现实：
Code Review 任务
→ 知道 review 标准（Skills）
→ 能拿到代码（MCP 调用 GitHub API）
→ 完美执行 review 流程
```

### 为什么 Skills 比 MCP 更重要？

**统计数据（2025-2026 实际使用）**：
```
100 个顾客点菜：
- 80 个：只需要菜谱（Skills）
  例："做个宫保鸡丁"（食材餐厅有）

- 15 个：需要菜谱 + 采购（Skills + MCP）
  例："做法餐"（需要进口食材）

- 5 个：只需要采购（MCP）
  例："去超市买瓶酱油"

结论：Skills 覆盖 95% 的场景
```

**实际应用映射**：
```
常见 AI 任务：
- 代码 Review → 需要 Skills（review 标准），不需要 MCP
- 写文档 → 需要 Skills（写作规范），不需要 MCP
- 架构设计 → 需要 Skills（设计模式），不需要 MCP
- 调试 Bug → 需要 Skills（调试方法），可能需要 MCP（读日志）

少数任务需要 MCP：
- 查 GitHub PR 状态
- 读取数据库数据
- 调用第三方 API
```

## Agent 自主性的演进

### Level 0：被动工具（2022-2023）

```
顾客："我要吃饭"
服务员："您想吃什么？"
顾客："川菜"
服务员："哪道川菜？"
顾客："宫保鸡丁"
服务员："什么辣度？"
顾客："微辣"
服务员："要花生吗？"
顾客："要"
服务员："多少克？"
顾客："50 克"
...

特点：每个细节都要顾客说，像"遥控玩具"
```

### Level 1：有一定理解（2024）

```
顾客："来份宫保鸡丁套餐"

服务员（开始推理）：
"套餐包括：主菜+米饭+小菜+汤，可以吗？"

顾客："可以"

特点：能理解常见需求，但需要确认方案
```

### Level 2：半自主规划（2025 初）

```
顾客："给我一顿川菜，4 个人"

领班（开始规划）：
"好的，建议：
- 凉菜：夫妻肺片
- 热菜：宫保鸡丁、麻婆豆腐、水煮鱼
- 主食：米饭
预计¥500，大约 1 小时，可以吗？"

顾客："可以"

特点：能规划完整方案，但需要用户批准
```

### Level 3：完全自主（2025 末-2026）

```
顾客："给我一桌川菜宴席，8 人，预算 2000，有人不吃辣"

领班（Agent 完全自主）：
[内心独白，不打扰顾客]
1. 查《川菜大全》→ 确定菜单结构
2. 计算预算分配 → ¥250/人，合理
3. 特殊需求 → 2 道不辣菜
4. 采购清单 → 去 MCP 拿食材
5. 排时间表 → 汤 3 小时前开始炖
6. 协调后厨 → 3 个炉灶并行
7. 质量把控 → 每道菜品尝

## 性能优化技术映射

### 1. Prompt Caching（备菜缓存）

**没有缓存的情况**：
```
第 1 个顾客点宫保鸡丁：
切葱姜蒜（5 分钟）→ 腌鸡肉（15 分钟）→ 炸花生（10 分钟）→ 炒制（5 分钟）
总耗时：35 分钟

第 2 个顾客点宫保鸡丁：
又要从头开始：切葱姜蒜（5 分钟）→ 腌鸡肉（15 分钟）...
总耗时：35 分钟

第 10 个顾客：还是 35 分钟
→ 慢、贵、浪费时间
```

**有缓存（备菜）**：
```
早上提前备好（这些是固定流程）：
- 切好一大盘葱姜蒜（可用一整天）
- 腌好 5 份鸡肉（冷藏待用）
- 炸好一大碗花生（密封保存）

顾客点单后：
直接拿备好的食材 → 炒制（5 分钟）→ 出菜
总耗时：5 分钟（快了 7 倍！）

成本：
人工：35 分钟 × 10 份 = 350 分钟 → 50 分钟（省 80%）
```

**对应 AI 技术**：
```
系统提示、工具定义（固定内容）→ 提前缓存
每次对话 → 直接用缓存，不重新处理

效果：
成本降低 90%（$3/M → $0.3/M）
延迟降低 85%（5 秒 → 0.5 秒）
```

### 2. Auto-Compact（收盘子，腾地方）

**没有压缩的情况**：
```
餐桌（上下文窗口）：
┌─────────────────────────────────┐
│ 空盘1 | 空盘2 | 空盘3 | ... │
│ 空盘10 | 空盘20 | 正在吃的菜 │
│ 空盘50 | ... | 空盘90 | 空盘100│
└─────────────────────────────────┘

问题：
- 100 个盘子占满餐桌（租金贵）
- 服务员传菜要绕一大圈（慢）
- 顾客找正在吃的菜很困难（信息噪音）
```

**压缩（收盘子）**：
```
服务员收拾：
- 空盘子收走
- 只留：正在吃的菜 + 菜单记录

结果：
┌─────────────────────────────────┐
│ 菜单记录 | 正在吃的菜1 │
│ 正在吃的菜2 | 正在吃的菜3 │
│ [大量空间] │
└─────────────────────────────────┘

100 个盘子 → 25 个盘子

效果：
- 租金降 75%（成本）
- 传菜更快（延迟降低）
- 找菜容易（用户体验好）
```

**对应 AI 技术**：
```
长对话历史（800K tokens）→ 自动压缩成摘要（200K）

效果：
成本降 60-75%
延迟降 50%
```

### 3. Skills 按需加载（选择性携带菜谱）

**老方式（全部携带 = MCP 方式）**：
```
厨师背着 50 本菜谱进厨房：
《川菜大全》《粤菜精选》《法餐圣经》
  《日料百科》《韩国料理》《东南亚风味》
  《烘焙宝典》《西餐礼仪》...

厨师：

问题：

```

**新方式（按需加载 = Skills 方式）**：
```
顾客点："宫保鸡丁"

## 关键洞察总结

### 1. 分层架构清晰

```
顾客层（用户）
    ↓ "我要川菜宴席"
服务层（推理层）← 最被忽视但最重要
    ↓ 理解+规划+优化
执行层（模型）
    ↓ 烹饪（生成）
工具层（MCP + Skills）
    ↓ 食材 + 菜谱
```

### 2. MCP vs Skills 的本质区别

```
MCP = 采购能力 = "我能拿到什么"
Skills = 烹饪知识 = "我知道怎么做"

单独的 MCP：有食材不会做 → 浪费
单独的 Skills：会做菜没食材 → 暂时做不了

最佳组合：MCP + Skills
（但 80% 的任务只需 Skills）
```

### 3. Agent 的自主性是关键突破

```
2022：顾客必须是烹饪专家（每个步骤都说）
2023：顾客要懂烹饪术语（详细描述）
2024：顾客说大概（厨师能理解）
2025：顾客说目标（领班自己搞定）
2026：顾客说需求（多领班协作完成）

→ 从"遥控玩具"到"自主同事"
```

### 4. 性能优化是工程问题

```
餐厅经营的艺术：
✓ 提前备菜（Caching）→ 快 7 倍
✓ 收空盘子（Compact）→ 省 75% 租金
✓ 选择性携带菜谱（Skills）→ 省 98% Token
✓ 智能索引（RAG）→ 快 100 倍

→ 不是单一技术，是组合优化
```

### 5. 演进规律：降低门槛

```
2022：只有专家能用（烹饪专家才会点菜）
2026：人人能用（说需求就行）

→ AI 正在从"专业工具"变成"大众助手"
```
