> 省钱这件事，最容易犯的错是盯着价目表砍单价，而不是盯着账单砍单任务成本。

先把三个数字放出来：

- 日均花费从 **$47.56 降到 $2.21**，降幅 95.4%
- 同期日均 token 只降到原来的 **39%**
- 三个月缓存命中率一直在 **90% 附近**，几乎没动

三条线放在一起，结论就有点反直觉了：**钱不是省在「少干活」上，也不是省在「缓存调优」上，而是省在「换了更便宜的模型」上。** 这篇文章把这个结论拆开：先看账单，再看外部基准，最后给一份能照抄的落地清单。

数据源是我自己 2026-07-01 到 09-15 的编码 agent 用量（4 种客户端、55 个模型、3.33B token），用 `ccusage` 按 agent 和模型聚合，口径问题写在最后一节。

## 1. 账单：三个月，日均 $47.56 → $2.21

| 月份 | 费用 | Token | 有效费率（$/M） | 缓存命中率 |
| --- | --- | --- | --- | --- |
| 2026-07 | $1,093.92 | 1.60B | $0.682 | 90.7% |
| 2026-08 | $296.87 | 1.42B | $0.209 | 88.6% |
| 2026-09（1–15） | $22.13 | 302.69M | $0.073 | 91.1% |
| **合计** | **$1,412.92** | **3.33B** | **$0.424** | **89.9%** |

![三个月费用、token 量与有效费率](/blog/images/cost-bill.webp)

*图：7 / 8 / 9 三个月的月费用、月 token 量与有效费率。费用掉了 96%，token 只掉了 81%，两条曲线不同步*

7 月有量的日子是 23 天，9 月到 15 日为止是 10 天。按**有量日**折算：$47.56/天 → $2.21/天。7 月和 8 月吃掉了总费用的 98.4%。

最值得盯的不是费用总额，而是**有效费率**：每百万 token 实际花了多少钱。它从 $0.682 掉到 $0.073，降了 89.3%。费率才是可迁移的知识——换个团队、换个月份，费用会变，费率背后的结构不会。

## 2. 归因：89% 的降幅来自「换模型」

把降幅拆成两个因子：

1. 把 7 月的**用量**按 9 月的**费率**结算：$47.56/天 → $5.09/天。这一刀是**价格 / 模型效应**，−$42.47，占降幅 89.3%。
2. 再把用量降到 9 月的水平：$5.09/天 → $2.21/天。这一刀是**用量效应**，−$2.88，再降 56.6%。

![成本下降归因瀑布](/blog/images/cost-attribution.webp)

*图：7 月实付 → 价格效应 → 用量效应 → 9 月实付。蓝色为实付端点，橙色为两个因子的贡献*

翻译一下：**同样的工作量，7 月的费率要花 9 倍的钱。** 我并没有变得更勤快，也没有突然少用 AI；结构变了，账单就变了。

这也解释了为什么「优化缓存」这类动作看起来正确却收效有限——它动的是费率的**折扣**，而动不了费率的**基数**。基数由「你让哪个模型干什么活」决定。

## 3. harness 没有绝对贵贱，贵贱取决于它挂的模型

7、8 月是 Claude Code 的独角戏（费用占比 99.8%、99.1%）。9 月客户端结构彻底换血：

| harness | 费用 | 费用占比 | Token 占比 | 有效费率 |
| --- | --- | --- | --- | --- |
| pi（pi-agent） | $16.89 | 76.3% | 47.1% | $0.118 |
| Claude Code | $3.37 | 15.2% | 17.7% | $0.063 |
| opencode | $1.16 | 5.2% | 27.1% | $0.014 |
| codex | $0.71 | 3.2% | 8.0% | $0.029 |

![harness 费用占比结构](/blog/images/cost-harness.webp)

*图：按费用占比堆叠。9 月 pi 占 47.1% 的 token，却占 76.3% 的费用*

两个反差：

- **pi 花掉 76.3% 的钱，只用了 47.1% 的 token。** 因为它挂的是前沿档模型（$0.118/M）。
- **opencode 用了 27.1% 的 token，只花 5.2% 的钱。** 费率 $0.014/M，比 pi 便宜 8 倍。

所以别急着给客户端排贵贱。**同一个客户端，挂什么模型，价差可以到 8 倍以上。** 这条观察在下一节的外部基准里被放大到了 17 倍。

## 4. 外部基准：单价便宜 ≠ 任务便宜

上面是我一个人的账。为了避免「一个人的账单只是特例」，看三组公开数据。

### 4.1 Sonnet 比 Opus 便宜 1.7 倍，单任务却更贵

Databricks 用自己代码库里真实合并过的 PR 构造了内部基准（跨 Python / Go / TypeScript / Scala，任务和测试都人工复核）：

| 指标 | Sonnet 5 | Opus 4.8 |
| --- | --- | --- |
| 每 token 价格 | 约便宜 1.7× | — |
| **单任务成本** | **$2.09** | **$1.94** |
| 任务完成率 | 81% | 87% |
| token 消耗量 | **1.9×** | 1× |

原因很朴素：Sonnet 5 为了把任务做完，**读得更多、跑得更久**，token 消耗是 Opus 的 1.9 倍。便宜的那部分单价，被多出来的 token 量吃掉了。

同一个基准里还有一条对国产模型很关键的数据：**GLM 5.2 的质量与 Opus 4.8 统计打平，单任务成本 $1.28 vs $1.94。** 也就是说，「便宜档模型」已经不是你印象里那个「便宜但干不完活」的角色了。

### 4.2 启动税：Aider 700 token，OpenClaw 26,000 token

The New Stack 汇总了三组独立基准，结论比上面更极端：

- **同样的模型、不同的 harness，每解决一个任务的 token 量从约 3,500（Aider architect 模式）到 292,000（OpenClaw），差 70 倍以上。**
- **「启动税」是主因**：harness 在干活之前，必须把自己的系统提示、工具描述、环境说明先发一遍。Aider architect 约 **700 token**，OpenClaw 约 **26,000 token**。带着 26K 的底噪跑 15 轮，≈ 39 万 input token 全花在脚手架上。
- **用「启动税 × 轮数」预测 token 消耗，R² = 0.99**——比「选了哪个模型」更能解释成本。

这条对我的影响最大：**轮数是乘数，底噪是系数。** 一次把需求和约束说清楚，好过十轮小步试探；把不用的 MCP 工具砍掉，比纠结模型便宜一档更有效。

### 4.3 固定模型只换 harness：通过率差 17 个百分点，成本差 17 倍

第三组数据来自 Runta 的 FrontierHarness v1.0——一次控制变量更彻底的评测：模型固定为 Kimi K3（统一走同一个网关），9 个 harness / 12 种配置，30 个任务（21 个 Terminal-Bench + 9 个 DeepSWE），360 次评估，每次都是同一份冷启动快照。**模型、任务、运行环境全不变，只换 harness。**

| Harness | 通过率 | 单次通过成本 | 缓存命中（median） |
| --- | --- | --- | --- |
| **Codex** | **66.7%** | $3.47 | 88.0% |
| DSH Creator | 63.3% | $3.28 | 84.3% |
| **Claude Code** | **63.3%** | **$18.34** | 67.8% |
| Pi | 60.0% | $2.43 | 79.4% |
| Exo Harness | 53.3% | **$1.05** | 70.3% |

三个可以直接引用的点：

1. **完成任务和便宜地完成任务，是两种独立能力。** Claude Code 和 DSH Creator 通过率完全一样（63.3%），单次通过成本 **$18.34 vs $3.28，贵 5.6 倍**。
2. **缓存命中率 ≠ 成本。** Claude Code 的 token 加权命中率只有 25.0%，中位数是 67.8%——因为三个最贵的任务占了它 88% 的 token。**中位数看「典型一次跑」，加权看「钱花在哪」。**
3. **厂商血统没有优势。** Kimi Code 由同一个实验室出品，排第七。

最难的那个任务把差距放大到 26 倍：Pi 和 Claude Code **都通过了**，但 Pi 用 90 轮、98.2% 缓存、$2.50；Claude Code 用 381 轮、15.7% 缓存、**$64.36**。

## 5. 成本公式：三层杠杆

### 5.1 公式

```
单任务成本 ≈ Σ_每一轮 ( fresh_input  × P_in
                     + cache_read   × P_cache_read
                     + cache_write  × P_cache_write
                     + output       × P_out )
```

三个变量、三层杠杆：**单价（P）、token 量（量）、缓存折扣（cache）**。只砍单价是收益最小的一种，但没有前三节的铺垫，很难相信这句话。

### 5.2 三档模型与真实倍数

按公开标价，把模型分成三档（每 1M token）：

| 档位 | 典型模型 | Input | Output | 适用 |
| --- | --- | --- | --- | --- |
| A · 便宜 | `glm-5.3-flash` / `deepseek-v4-flash` | $0.19 | $0.51 | 翻 flag、改配置、查日志、跑测试 |
| B · 主力 | `glm-5.3` / `kimi-k3` / Sonnet 档 | $0.19–3.00 | $0.51–15.00 | 日常 feature、bug fix、代码审查 |
| C · 高难 | Opus 档 / `gpt-5.6-terra` | $3.00+ | $15.00+ | 架构设计、跨模块重构、疑难调试 |

A 档与 Sonnet 档的**标价**差 15.8×（input）到 29.4×（output）。按真实 agent 流量（input 远多于 output）混算「1M output + k × 1M input」这样一个「任务单位」：

| Input : Output | 标价倍数 | 含缓存倍数（Sonnet 按 90% 命中、便宜档按全价估） |
| --- | --- | --- |
| 1 : 1 | 25.7× | 22.2× |
| 10 : 1 | 18.7× | 8.6× |
| 24 : 1（agent 典型） | 17.2× | 5.7× |
| 80 : 1（长上下文密集） | 16.2× | 3.9× |

三句话读这张表：

1. **标价差 16–29 倍，账单差 4–9 倍。** agent 流量是 input 密集型，缓存把便宜档的优势削掉一大截。
2. **本次审计的实测费率差是 9.3 倍**（$0.682 / $0.073），正好落在这个区间的上沿——理论和账单对上了。
3. 所以「换便宜模型」不是 20 倍的神话，是 **4–9 倍**的现实。4–9 倍依然值得做，只是别拿 20 倍去立军令状。

另外两个必须说清楚的坑：

- **缓存折扣只改单价，不改 token 量。** 便宜模型可能更费 token——参考 4.1 里 Sonnet 5 的教训。要用**单任务成本**验证，不能只看单价。
- **价格随时会变。** 上游有促销价、网关报价未必同步，做对比时必须标注**取价日期**。

## 6. 缓存：我原来的结论错了一半

这是我写这篇文章时最大的修正。

### 6.1 先修口径：那个 17% 是分母的错

之前我用一份按**会话**聚合的报告，得出「Claude Code 接第三方模型时缓存命中率只有 17%–36%」，并据此写了「先把缓存打通，再谈换模型」。

换到按 **token 加权**、且分母统一为「该模型处理过的全部 prompt token」之后：

![原生模型 vs 第三方模型的缓存命中率](/blog/images/cost-cache.webp)

*图：2026-07 / 08 / 09 三个月，Anthropic 原生模型与第三方模型的缓存命中率对比。合计 94.3% vs 85.2%*

| 分组 | prompt token | 未命中 token | 命中率 |
| --- | --- | --- | --- |
| Anthropic 原生模型 | 1.49B | 84.41M | **94.3%** |
| 第三方 / 网关模型 | 1.53B | 227.15M | **85.2%** |

差了 9.2 个百分点。换算成「全价 input」，未命中比例是 5.7% vs 14.8%，**差距 2.62 倍**。

但和我原来的结论相比，85.2% 和 17% 完全是两个世界。差别只有一件事：**统计单位**。

- 按会话平均：长会话、冷启动会话会把均值拖到很低，且不同会话的量级差几十倍，均值没有意义。
- 按 token 加权：钱是按 token 付的，只能看 token 加权。

这跟 4.3 里那条「中位数 67.8%、加权 25.0%」是同一个教训的两面。**做成本分析时，先问一句「这个百分比是按什么分母算的」，比看数字本身重要。**

顺带一个跨厂商的记账差异：Anthropic 模型报三段式（`input` 未命中 / `cacheCreation` 写缓存 / `cacheRead` 读缓存），而第三方模型的 `cacheCreation` **恒为 0**——它们的缓存是隐式自动的，「写」被并进了 `input`。所以跨厂商可比的口径只能统一成 `cacheRead / (input + cacheCreation + cacheRead)`。若换成 `cacheRead / (input + cacheRead)`，Anthropic 会虚高到 99.7%，属于口径不一致。

### 6.2 缓存不是降本来源，是护栏

修完口径，结论反而更清楚了：

- 三个月缓存命中率 89.9%，波动不到 3 个百分点。**它没变过，所以它不可能是降本的原因。**
- 但它是**护栏**：命中率掉 10 个点，等于 input 成本涨约一倍。它不会让你省钱，但会让你突然变贵。

所以正确的定位是「**别让它变差**」，具体做法：

- **缓存有 TTL，默认 5 分钟。** 1 小时档要显式开启，写入价按 2× input 计（5 分钟档是 1.25×）。发呆太久 = 缓存过期 = 下一轮全量重算。
- **会话中不要切模型 / 切后端。** 换模型会切换缓存命名空间，之前的缓存全部作废。**要切就开新会话切。**
- **长任务做完就收尾。** `/compact` 压缩，或直接 `/clear` 开新会话，别把无关历史一直拖着。
- **跨会话交接用交接摘要。** 生成一份精简的交接文档，新会话按需加载，而不是把整段历史 resume 回来。
- **批量任务集中在同一时间窗做完。** 同一个文件一天分十次碰，缓存基本每次都是冷的。
- **会话中途不要改 `CLAUDE.md` / `settings.json` / MCP 配置。** system prompt 一变，缓存立刻失效。

## 7. 启动税：每一轮都付的固定开销

如果说换模型是「砍单价」，这一节是「砍量」——而且砍的是最没意义的那部分量。

![Claude Code 的 /context 输出](/blog/images/cost-context.webp)

*图：`/context` 的实际输出。96.8K / 1M token（10%），其中 System tools 37K、MCP tools 35.3K、Skills 10K*

这一屏里最值钱的三个数字：

- **System tools：37K**（工具描述）
- **MCP tools：35.3K**
- **Skills：10K**

工具描述一项（37 + 35.3 = 72.3K）就占了已用上下文的**四分之三**。它们每一轮都要重发一遍，按 4.2 的算式，这就是「启动税 × 轮数」。

按 30 轮算：72.3K × 30 ≈ **2.2M token**，全花在工具 schema 上。哪怕命中缓存打到 0.1× 的折扣，账也不小。

清理清单（按收益排序）：

- **精简 MCP。** 不要配全局，改成**项目级按需启用**；能用 CLI 就别用 MCP（`gh`、`curl` 够用）；定期 `/mcp` 看哪些 server 实际在跑。
- **精简 Skills。** Skill 的 `description` 常驻 system prompt，skill 越多底噪越重。「元技能」会级联加载大量子技能，轻任务不要触发；不需要自动匹配的 skill 加 `disable-model-invocation: true`。
- **精简 `CLAUDE.md` 和全局规则。** 全局规则越长，每轮越贵，只留真正必要的。
- **注意 statusline / hooks 的固定开销**，例如每条 shell 命令都调一次的安全分类器。

## 8. 任务分层：85% 的任务不该找最贵的模型

Databricks 的基准里还有一个数字很实用：工程师的日常任务里，约 **25% 是低复杂度、60% 是中复杂度、15% 是高复杂度**。

| 复杂度 | 占比 | 典型任务 | 建议档位 |
| --- | --- | --- | --- |
| 低 | ~25% | 翻 flag、改配置、查日志、格式化、跑测试 | A（flash 档） |
| 中 | ~60% | 日常 feature、bug fix、code review、批处理 | B（glm / kimi / Sonnet） |
| 高 | ~15% | 架构设计、跨模块重构、疑难调试 | C（Opus 档 / 前沿档） |

**默认用最贵模型，等于让 85% 的任务为 15% 的需求买单。**

要让这件事真的落地，前提是**换模型足够便宜**——如果你换一次模型要改配置、开新终端、改 profile，那你永远不会换，最后所有任务都会落在最贵那一档。我的做法是一套 CLI 加几个 shell 别名（`cc glm`、`cc kimi`、`cc fast`），一行命令切档。

一个容易踩的坑：**`--model` 只管主线程，管不住旁路。** 子代理 frontmatter 里写死的 `model`、Agent 工具的 `model` 参数、hook 的 haiku 档、会话标题生成、auto 模式的安全分类器（每条 shell 命令都调一次）——这些入口会绕过你指定的模型，悄悄产生计费。与其逐个改，不如在**别名解析层**重映射一次覆盖全部：

```bash
export ANTHROPIC_DEFAULT_OPUS_MODEL="$MAIN"    # opus 别名
export ANTHROPIC_DEFAULT_SONNET_MODEL="$MAIN"  # sonnet 别名
export ANTHROPIC_DEFAULT_HAIKU_MODEL="$FAST"   # hook / 小任务
```

## 9. 落地清单

**今天就能做：**

1. 跑一次 `/context`，看自己的启动税有多重。工具描述超过 30K 就该动手了。
2. 清掉不用的全局 MCP 和 skill，改成项目级按需加载。
3. 记住两条：**切模型 = 开新会话**；**长任务结束 = `/compact` 或 `/clear`**。

**这周能做：**

4. 用 `ccusage`（或 `/cost`）记录一周的真实花费**基线**，算出有效费率（$/M token）。
5. 挑一类低复杂度任务切到 A 档，对比**单任务成本**和完成率——不是对比单价。
6. 把「同文件多次小改」合并成一次会话。

**持续做：**

7. 每周看一次缓存的 `cache_breaks`（缓存失效落在哪几轮），它是护栏，不是油门。
8. 每月看一次费率与 token 结构的趋势，重点看「钱花在哪个价位档」，而不是总额。
9. 新模型上线时，用**自己的任务**测单任务成本，而不是看榜单单价。

**度量原则只有一条**（来自 Databricks）：**看「单任务成本 / cost per verified outcome」，不要看「每 token 成本」。** 后者忽略了通过率和缓存档位，会给出错误的排序。

## 10. 数据边界：这些数字该怎么读

一份诚实的账，必须说明它的偏差。三处：

**一、第三方模型是挂牌价估算。** `ccusage` 对 Anthropic 模型的成本基本可信（7–8 月的账单主要由它们构成），但对第三方模型它用的是公开价目表，与实际结算未必一致。若你用的是包月/包量套餐，文中「费用」应理解为**等价算力成本**，而非实付。

**二、价目表有缺口，已按官方价修正。** 审计里出现过某模型报 $0.00 却有 238M token 的情况——是价目表缺条目，不是真免费（同一模型不带 `org/` 前缀时能正确定价）。按官方价重算后：7 月 $1,093.92 → $1,132.40（+4%），8 月 $296.87 → $395.35（+33%），9 月 $22.13 → $32.46（+47%）。**即使取修正后的上限，日均费用仍是下降 95% 以上的量级，结论不变。**

**三、9 月是半个月。** 数据截至 15 日，其中 10 天有实际用量。按自然日外推 $44.27，按活跃日外推 $66.40。对照 7 月 $1,093.92 与 8 月 $296.87，全月大概率落在 $44–$66，不影响量级。

还有一层偏差来自归因本身：**归因是我做的分解，不是实验。** 我在自己真实的工作流上换模型、换客户端，没有做严格 A/B。文中引用的外部基准（4.1–4.3）才是控制变量的实验，我的账本只是「在真实环境里是否复现」的旁证。

## 附录：模型路由的后缀是什么意思

网关上的模型名末尾常带一个后缀，比如 `-anthropic`、`-aws`、`-azure`、`-gcp`。**后缀是托管方（hosting route），不是版本号。** 同一个模型可以挂在多家托管服务器上，后缀不同 = 物理后端不同 = 价格、缓存行为、可用能力都可能不同。

| 后缀 | 托管方 |
| --- | --- |
| （无） | 自动路由，网关自行挑一条 |
| `-anthropic` | Anthropic 直连 |
| `-aws` | AWS Bedrock |
| `-gcp` | Google Cloud Vertex AI |
| `-azure` | Microsoft Azure AI Foundry |

**做成本对比必须固定同一条路由**，否则倍数不可比。同一模型走不同托管方，报价和缓存行为都可能不一样——这也是为什么文中所有价格都标注了取价日期与路由口径。
