2024 年 11 月，Anthropic 发布 MCP（Model Context Protocol）。它被叫作「AI 工具的 USB-C 接口」——这个比喻流传得太成功，以至于很多人以为插上就能用。

真正的问题从来不是「能不能插上」，而是「插上之后，谁付代价」。

## 它到底解决什么

MCP 出现之前，每一家模型厂商、每一个 Agent 框架，都在用自己的方式定义「怎么调用外部工具」。五个模型配十个系统，理论上要写五十套适配。

```
没有 MCP： 模型 × 系统 = N × M 套适配
有了 MCP： 模型 + 系统 = N + M 套适配
```

协议本身不复杂：跑在 JSON-RPC 2.0 之上，服务端暴露三种原语——工具（可执行的动作）、资源（可读取的数据）、提示（预设的模板）；客户端则提供采样、根目录等反向能力。一次握手，双向发现。

工程上的收益很直接：**集成从「一次性开发」变成「一次配置」**。这也是它能在半年内被主流厂商陆续接受的原因——不只是 Anthropic，OpenAI、Google 也先后宣布支持。

## 800 万次下载之后，问题才刚开始

热度最高的时候，MCP Server 生态的下载量以百万计。但把 MCP 真正接进生产环境的人，很快撞上三堵墙。

**第一堵：Token 账。**

工具不是免费的。每一个 MCP Server 暴露的工具定义——名字、描述、参数 schema——都要进上下文。接十个 Server，可能几百个工具，光「告诉模型它有哪些工具」就吃掉可观的预算，还挤占了真正用于推理的空间。

这催生了一个反直觉的工程结论：**接得多不等于能力强**。工具数量增加时，模型的工具选择准确率反而可能下降——它不是更聪明了，只是被选项淹没了。

**第二堵：安全边界。**

MCP 的设计默认了一个假设：服务端是可信的。现实里这个假设经常不成立。

- 工具描述可以由服务端任意书写，这意味着**提示注入有了新的载体**——一段恶意的工具说明，就足以改变模型的行为。
- 权限粒度粗。给了文件读取，往往就意味着给了整个目录。
- 供应链问题被放大。一个被投毒的第三方 Server，能接触到的上下文可能远超预期。

**第三堵：企业治理。**

个人用 MCP 是「装个插件」，企业用 MCP 是「谁能装、能连什么、出问题谁负责」。审计日志、白名单、最小权限、数据出境——这些在演示里不存在，在落地时是前置条件。

## MCP 和 Skills 不是一回事

这是最容易被混淆的一点，也是我在企业内推动落地时纠正最多的认知。

| | MCP | Skills |
| --- | --- | --- |
| 回答的问题 | AI **能连什么** | AI **知道怎么做** |
| 本质 | 连接协议 | 知识封装 |
| 失败表现 | 连不上、调不通 | 连上了，但做得不对 |
| 类比 | 采购系统 | 菜谱 |

两者是**正交**的，不是竞争关系。有 MCP 没 Skills，是「手里有刀但不会切菜」；有 Skills 没 MCP，是「知道怎么做但拿不到食材」。

企业里最常见的错误，是把两者当成同一份预算里的替代选项去比较——结果要么买了一堆连不通的规范，要么攒了一堆用不上的手册。

## 它是能力层，不是智慧层

三年看下来，MCP 的位置其实很清楚：它把「AI 能不能碰到外部世界」这个问题标准化了，但没有、也不打算解决「碰到之后怎么做才对」。

判断一项 MCP 投入值不值，我的标准是三条：

1. **它是否替代了原本要写死的集成代码**——是，则收益立刻兑现。
2. **它的工具数量是否可控**——超过三十个，就该考虑拆分或按需加载。
3. **它是否有明确的权限边界与审计出口**——没有，就先别进生产。

协议会继续演进，工具会继续变多。但那条线不会变：**连接解决的是可能性，判断解决的是正确性**。前者靠协议，后者只能靠领域知识和工程约束。
